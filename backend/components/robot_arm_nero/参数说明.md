# robot_arm_nero（NERO 机械臂）组件参数说明

`backend/components/robot_arm_nero/config.json` 是本组件唯一的配置入口（JSON 不支持注释，本文档就是它的注释）。**改本文件需重启后端**（组件实例在进程启动时构建一次）。

本组件把骰子游戏的机械臂动作（抓杯 / 摇骰 / 胜负手势 / 归位）桥接到 **dice_demo 常驻控制进程**（`bash run.sh control --execute`，官方契约见 `dice_demo/docs/INTEGRATION.md` §2）。进程在首个 dice 回合创建时后台拉起（规则宣读约 30s 覆盖其 6-10s 预热），跨回合保活，服务退出时优雅关闭；进程死亡（阶段失败退出码 2 / SIGINT 130）后下一条命令自动重启。

## 1. config.json 逐键

| 字段 | 当前值 | 说明 |
|---|---|---|
| `demo_root` | `../dice_demo` | dice_demo 仓库根，**相对主仓库根解析**。默认指向兄弟仓库（板端 `/home/spacemit/projects/dice-game/dice_demo`，分支 `hwj_dev`）。demo 不入本仓库 git、也不入分发包——它有自己的发布流程（`scripts/package_release.py`），部署新板时两个仓库并排摆放 |
| `python_bin` | `/usr/bin/python3` | 注入给 demo 的 `DICE_VISION_PYTHON` / `DICE_SDK_PYTHON`（demo 的 `env.sh` 会回退到系统 python，这里显式钉死） |
| `ready_timeout_seconds` | `60` | 等常驻进程 `ready` 事件的上限（SDK/CAN 连接 + 相机预热 + 模型加载实测 6-10s；can0 未拉起时进程会秒退，错误信息带 controller.log 尾部） |
| `grasp_timeout_seconds` | `45` | `grasp_cup`（advance until GRIP）总预算，**含进程死亡后的自动重启预热**。常驻热机下实测抓取 2-3s |
| `shake_timeout_seconds` | `120` | `shake_dice`（advance until RETURN_HOME：摇+放杯+张手+归位一条链）总预算 |
| `action_timeout_seconds` | `30` | 静态动作（胜负手势 / 归位）预算 |
| `sigint_grace_seconds` | `15` | 取消/超时后 SIGINT 进程组到 SIGKILL 的宽限 |

## 2. 游戏命令 ↔ demo 命令映射

| 游戏动作（manifest `{"action":"robot",...}`） | demo stdin 命令 | 完成判据（id 关联） |
|---|---|---|
| `grasp_cup` | `{"command":"advance","until":"GRIP"}`（HOME→CAPTURE→PLAN→APPROACH→GRIP，识别+抓取**不摇**） | `command_completed` |
| `shake_dice` | `{"command":"advance","until":"RETURN_HOME"}`（LIFT→SHAKE→LOWER→OPEN→RETURN_HOME） | `command_completed`（RETURN_HOME 完成还会发 `run_completed` 并自动复位空闲） |
| `feedback` win/lose/draw | 先发 `{"command":"reload"}` 热重载手势表，再 `{"command":"action","name":"yeah"/"thumbs-up"/"tie"}` | `action_completed` |
| `reset_home` | 同上（reload + `{"command":"action","name":"home"}`）；**常驻进程不在时直接跳过不重启**（best-effort） | `action_completed` |

进度：demo 的 `phase_started` 事件直译成 `{"event":"robot","phase":...,"zh":...,"progress":"n/10"}` 进回合事件流（十阶段中文表在 `provider.py` 的 `_PHASE_LABELS_ZH`）。

**手势热重载（demo 2026-09-23 起）**：胜负手势与归位配方在 `configs/actions/gestures/` 分组目录（含 `result_feedback.json` 组；动作名 yeah/thumbs-up/tie 与别名 win/lose/draw 不变）。每个静态动作命令前组件自动发一条 fire-and-forget `reload`——demo 串行处理 stdin，改手势文件后**下一个手势即用新表**，无需重启常驻或后端；reload 失败（文件非法/流程中）按 demo 契约保留旧表继续。

## 3. 韧性行为（真机相关）

- **串行锁**：同一条臂一次只跑一条命令（后到的命令排队，游戏里"倒计时抓取未完、摇指令已下发"就是靠这个自然衔接）
- **Hand-start 自动重跑**：失败原因含 `Hand start`（手指位移、预动校验不过）时自动重启进程重跑一次，真机验证过可恢复。demo 2026-09-23 调机后容差已放宽（`hand_start_tolerance_deg` 0.5°→1.0°、SHAKE 反馈新鲜度 0.1s→0.3s 且起点偏差先重采样重规划、LOWER 放杯偏差 record 模式不再失败），`arm_failed` 概率应显著下降——出现仍属正常，蓝键重试即恢复
- **取消语义**：回合取消/终态 → 进程组 SIGINT → 宽限后 SIGKILL（demo 现实现 SIGINT 即进程退出 130，下条命令重启）
- **失败后状态一致**：`failed` 事件（进程退出）后主动收割进程并丢弃句柄，健康检查/跳过逻辑即时一致

## 4. 部署与运维

- **can0**：`start_web.sh` 有幂等自检（接口在但 DOWN 时无 sudo 尝试拉起，失败仅警告）；板子重启后需人工一次 `sudo ip link set can0 up type can bitrate 1000000`
- **硬件**：D435i 占 `/dev/video1-6`、C920 漂到 video7 → 两游戏裁决相机已改 by-id 路径（见 `backend/games/*/adjudicator_config.json`）
- **健康检查**：`health()` 只做部署完整性检查（run.sh / configs/green_cup.json / vendor-site 两件），不碰硬件
- **换桌面/重标定**：demo 侧有多重硬绑定（标定哈希、桌面登记），换桌后须按 `dice_demo/docs/CALIBRATION.md` 重做，常驻进程会在 `ready` 之前就失败（日志在 session 目录 `controller.log`）
- **排障**：每次常驻启动一个新 session 目录 `<demo>/cup_grasp_demo/datasets/game_<时间戳>_<uuid>/`，`controller.log` 是 demo 的 stderr 全量，`green_pipeline_state.json` 是阶段状态
