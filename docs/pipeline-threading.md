# 多线程流水线改造说明书（A|B 双线程）

> 本文记录 2026-09-15 的线程化改造：为什么要拆、为什么这么拆、怎么验证。
> 结论：**只加 1 个线程（B），把检测切成 A/B 两阶段做流水线**。

## 1. 改造前的现状

### 1.1 处理环节没有分开

改造前只有 **1 个工作线程**：

```
主线程:    采集(7.5ms) → 检测(41.6ms)     ← 严格串行
                                    ↓
RTSP线程:                    画标注 → H.264 编码   ← 已移出主路径
```

而且检测**内部**也没有阶段划分：`fitShapeRobust()` 是在轮廓循环里**逐轮廓**调用的，
所以"建掩码 / 找轮廓"和"拟合 / 验证"是**交错**执行，不是一个接一个的阶段。

### 1.2 阶段耗时（30 张干净帧实测）

测量方法：用 `--method mask` 排除 Hough 干扰，再用"收紧半径区间让候选在预筛被拒"
的方式把 A 阶段单独量出来（仅剩像素处理，不进拟合）。

| 阶段 | 耗时 | 构成 |
|---|---|---|
| **A** 像素 → 候选 | **18.0 ms** | resize 0.63 + cvtColor 1.16 + inRange 1.35 + CLOSE 7.04 + OPEN 4.11 + 泛洪填洞 1.31 + findContours 0.60 + 预筛 |
| **B** 候选 → 结果 | **23.6 ms** | 椭圆 RANSAC 拟合 + 环带验证 + 打分/去重/排序 |
| 合计 | 41.6 ms | |

> ⚠️ **B 反而更大**（不是直觉里的 A 更大）。这个数据直接决定了切分点的选择。

### 1.3 端到端

| 指标 | 值 |
|---|---|
| 检测/帧 | 41.6 ms（含取流则约 48~49 ms） |
| 端到端帧率 | **20~21 fps** |
| 相机上限 | **30 fps**（`v4l2-ctl` 确认 1280x720 MJPG 支持 30/24/20/15…） |

推流开关对帧率无影响（21.2 vs 21.3 fps）—— 说明批次 1 的"叠加图移出主路径"已生效。

## 2. 为什么选 A|B 切分

### 2.1 候选切分点对比

| 切分点 | T1 | T2 | 吞吐 | 评价 |
|---|---|---|---|---|
| **A \| B（选定）** | 7.5+18.0 = 25.5 | 23.6 | **39 fps** | 负载均衡、语义干净 |
| 掩码 \| (轮廓+拟合) | 22.6 | 26.0 | 38 fps | 略差，且切在 A 内部 |
| 采集 \| (A+B) | 7.5 | 41.6 | 24 fps | ❌ 不达标 |
| 采集\|A\|B（3 线程） | 7.5 / 18.0 / 23.6 | — | 42 fps | 超相机上限，无收益 |
| 不拆（改造前） | — | 49.1 | 20 fps | — |

**T1 = 25.5 ms、T2 = 23.6 ms 都低于相机节拍 33.3 ms → 稳定跑满 30 fps，余量约 8 ms。**

### 2.2 关于线程数：计划 2 线程，实测后改成 3 线程

**原计划**：A|B 两阶段足够（T1=25.5ms、T2=23.6ms 都低于相机 33.3ms），
采集独立出去只能把吞吐从 39 提到 42 fps，而相机上限 30 fps，看似无收益。

**实测推翻了它**：真机上 A|B 反而**比顺序慢**（10.0 vs 11.6 fps）。
逐段计时找到原因：

```
顺序    取帧 18.5ms + A 18.4ms           = 37.0ms
A|B     取帧 35.3ms + A 18.5ms（B 并行） = 53.8ms
        ^^^^^^^^^ 取帧从 18.5 涨到 35.3ms
```

**MJPEG 解码与 B 线程争抢**（内存带宽/缓存），主循环被采集拖住。
把采集独立成线程后取帧回到 18.5ms 量级，收益才显现。

所以最终是 **3 个线程**：采集 / A+B / RTSP。
教训：静态算负载均衡不够，争抢效应必须实测。

## 3. 设计

### 3.1 线程图（最终形态：3 个工作线程）

```
采集线程              主线程                    B 线程              RTSP 线程
  ├─ read (18.5ms)      │                          │                  │
  └─ push CaptureFrame ─>│                          │                  │
     q_cap              ├─ A 阶段 (18.5ms)          │                  │
                        ├─ push CandidateSet ──────>│                  │
                        │  q_ab                    ├─ B 阶段 (13.7ms) │
                        │                          └─ push DetectJob ─>│
                        ├─ 消费 DetectJob <────────┘   q_bm           ├─ drawOverlay
                        ├─ JSON / 调试图 / 存视频                       ├─ VPU H.264 硬编
                        └─ 回循环                                       └─ rtspclientsink
```

三个队列都是**单槽 latest-only**：生产者替换旧任务而非排队，
所以采集永不阻塞，慢的阶段只跳过旧帧、永远处理最新帧。

主线程保留 `imshow` / 信号处理 / 优雅退出 —— GUI 与信号有线程亲和性要求，
不适合挪到工作线程。

### 3.2 队列：单槽 latest-only

照搬参考工程 `yolo_segdetect/src/latest_queue.h` 的设计：生产者**替换**旧任务
而不是排队等待，所以采集永不阻塞，慢的阶段只是跳过帧、**永远处理最新帧**。

对实时视觉这是正确的语义：宁可丢旧帧，也不要让延迟累积。

### 3.3 数据结构

```cpp
// A 阶段的产物。B 阶段需要的东西全部带上，避免重算。
struct CandidateSet {
    std::shared_ptr<const cv::Mat> frame;  // 原始 BGR（B 的验证 + RTSP 绘制要用）
    cv::Mat hsv;                           // ★ 预计算，见 3.5
    cv::Mat mask;                          // overlay 的 mask_inset 要用
    std::vector<std::vector<cv::Point>> contours;
    int    mask_count;                     // 供 B 判断"场景是否变化"
    double scale;
    long   index;                          // 真实帧号（丢帧时不能靠计数推断）
};

struct DetectJob {
    std::shared_ptr<const CandidateSet> cs;
    DetectResult res;
    double a_ms, b_ms;                     // 分段计时，便于验收
};
```

`CircleDetector` 暴露两个方法；顺序模式由它们组合，
**保证两条路径共用同一份实现，不会分叉**：

```cpp
CandidateSet extractCandidates(const cv::Mat& bgr, long index);  // A
DetectResult fitCandidates(const CandidateSet& cs);              // B
DetectResult detect(const cv::Mat& bgr);   // = A + B（顺序模式 / 自检用）
```

### 3.4 跨帧状态的归属（最容易出错的地方）

`CircleDetector` 有 4 个跨帧成员：

```
hough_cooldown_left_    hough_useless_streak_
prev_mask_count_        last_used_hough_
```

**全部归 B 线程** —— 因为 Hough 触发、冷却计数、结果判定都在 B。

- A 的候选数通过 `CandidateSet::mask_count` **传递**给 B，而不是让 B 去读 A 的对象
- 因此 **B 线程独占一个 `CircleDetector` 实例**
- 代码里用注释显式写明这一点，否则以后有人加状态就可能踩线程安全

### 3.5 修掉一处批次 3 引入的低效

批次 3 把 `validateShape` 的入参从 `hsv` 改成 `bgr` 后，它**在函数内重算整图
`cvtColor(bgr→hsv)`**（`circle_detector.cpp:424-425`），而它是**逐候选**调用的 ——
2 个候选就白烧约 2.3 ms。

修法：`CandidateSet` 带上预计算的 `hsv`，`validateShape` 接收它。
**纯去重复计算，不改变任何判据。**

### 3.6 配置与回退

```json
"pipeline": { "enabled": true }
```

`enabled: false` 时走顺序路径（同一份 A/B 实现），用于：
- 逐帧一致性验证（两条路径对拍）
- 出问题时的即时回退开关

## 4. 精度保证

### 4.1 为什么单帧无损

对**任意一帧**，A、B 内的代码路径、参数、RANSAC 种子
（`20260915u + 7919*iter`，固定）**完全不变**。线程只让"第 N 帧的 B"
与"第 N+1 帧的 A"重叠执行。

### 4.2 两条如实说明的保留

1. **跨帧状态演化可能不同**：`hough_cooldown_left_` 依赖"处理了哪些帧"。
   latest-only 丢帧后，冷却的**时机**可能与顺序模式不同。
   **单帧结果不受影响，但连续行为可能有细微差异。**
2. **丢帧本身**：顺序模式其实**已经在丢帧**（检测 48 ms vs 相机 33 ms/帧，
   且 `CAP_PROP_BUFFERSIZE=1` 每次拿最新帧）。流水线只会处理得更多、且总是最新帧。

因此本方案的主张是：**同一帧的所有逐帧结果完全一致（可验证）**，
而不是"绝对零影响"。

## 5. 验收标准

| 检查 | 门槛 | 方法 |
|---|---|---|
| **逐帧逐位一致**（最强证据） | 图片源 30 帧，`pipeline on` 与 `off` 的 cx/cy/r **完全相同** | 脚本对拍 |
| 相机路径共有帧号一致 | 两版共有 `index` 的结果必须相同 | 脚本对拍 |
| 30 干净帧半径差 | 平均 ≤ 0.1 px、最大 ≤ 0.3 px | 复用 `/tmp/ev` |
| `--self-test` | 7 项 17 断言全过 | |
| `tools/eval.sh` | 全过 | |
| 三样本半径 | 保持 119.0 / 121.1 量级 | |
| 端到端帧率 | **必须实际提升**（预期 21 → 30 fps） | `--summary` 的 wall/frames |
| RTSP 输出 | 标注内容不变，`drawMsAvg()` 不成为新瓶颈 | 拉流抓帧 |

**若"逐帧逐位一致"不成立 → 立即停止排查，不提交。**

## 6. 风险与回退

| 风险 | 缓解 |
|---|---|
| 数据竞争 / 死锁 | B 独占 detector 状态；队列全走 mutex；退出按 主→B→RTSP 固定顺序 join |
| 丢帧导致行为差异 | 只影响"处理哪些帧"，不影响"同一帧的结果"；有 `enabled:false` 回退 |
| RTSP 线程成为新瓶颈 | 已有 `drawMsAvg()` 埋点，验收时检查 |
| 帧号错乱 | `index` 随数据结构传递，不靠计数器推断 |
| 精度退化 | 每步都跑逐帧对拍，不一致就不提交 |

## 7. 实测结果

### 7.1 真机端到端（交替 3 轮，各 80 帧，抵消环境漂移）

| 配置 | processed_fps | result_fps | 检测耗时 |
|---|---|---|---|
| 完全回退（顺序 + 同步采集） | 16.4 / 16.3 / 16.4 | 同左 | 37.7 / 38.7 / 38.2 ms |
| **A\|B + 采集线程** | **25.5 / 25.5 / 25.6** | 22.0 / 23.9 / 24.6 | 37.0 / 37.7 / 38.8 ms |

**25.5 vs 16.4 fps = 1.56×，且检测耗时相同 → 提升纯来自重叠。**

### 7.2 单图源（无相机节拍限制，看算法上限）

| 配置 | fps | ms/帧 |
|---|---|---|
| 顺序 | 28.6 | 35.0 |
| **流水线** | **51.2** | **19.5** |

**1.79×**，超过相机 30fps 上限 —— 说明在真机上现在已经**被相机节拍限制**。

### 7.3 指标说明（重要）

之前"fps"混淆了两个概念，summary 现在同时输出：

- `processed_fps` = 真正处理了多少帧（**吞吐，看这个**）
- `result_fps` = 产出了多少结果（B 比主循环快时，旧结果会被
  latest-only 覆盖丢弃，所以这个值偏低是正常的、也是设计意图）

### 7.4 一致性验收

| 检查 | 结果 |
|---|---|
| 流水线 vs 顺序，共有帧逐帧逐位 | ✅ 24/24 完全一致 |
| 顺序模式 vs pre-pipeline 存档版 | ✅ 30/30 完全一致 |
| `--self-test` | ✅ 7 项 17 断言全过 |
| `tools/eval.sh` | ✅ 全过 |
| RTSP 标注（流水线下拉流抓帧） | ✅ 圆环/十字/长短轴/标签/HUD/掩码小窗完整 |
| 编码线程绘制耗时 | 11.1 ms |

### 7.5 回退开关

```
--no-pipeline        关 A|B，走顺序路径
--no-capture-thread  关采集线程
两个都加 = 完全回到改造前行为
```
