# 第一部分：当前项目（main 仓）

## T-0 时序与动作同步专题（2026-09-25 深挖，当前最优先）——`待讨论`

**问题本质：两个时钟，零握手。** 游戏侧时钟（状态机 duration + 预录 wav）与物理侧时钟（臂执行链真实耗时）各自跑，中间只有一次单向派发 + 一次完成回执，同步靠把 duration 常数调得逼近物理时长（开环控制）。物理波动（换桌/负载/CAPTURE 慢一拍）直接穿透成节奏错位；09-24 的调参（game_start 3.0→3.5、finger 0.5→0.3）本质是给开环系统手动重标定，会反复回来。

### 四个同步点（dice/rps 全链真正需要对齐的地方）

| # | 同步点 | 需要的关系 | 现状锚点 | 错位表现 |
|---|---|---|---|---|
| ① | LIFT 完成 ↔ 倒计时起点 | 臂举好杯才开始"三二一" | 固定 duration 3.5s | 臂快→空窗；臂慢→"开始"喊完臂没动（shake_dice 在锁上排队） |
| ② | "开始"口令 ↔ SHAKE 起转 | 同刻 | on_expire 派发 + 锁排队 | ~100-300ms，观众基本无感 |
| ③ | 放杯完成 ↔ 喊"停" | 手指松开杯子就喊停 | shake_dice.completed = RETURN_HOME 完成 | 晚 ~1s：臂已回 home 才喊停，玩家节奏被带偏 |
| ④ | rps"布" ↔ 亮拳 | 口令落点亮拳 | delay_seconds=0.0 整链即发 | 抢跑/错位（"拿捏不准"的主诉） |

### 演进路线（按侵入度三档，推荐 L1 → L2 → 重评 L3）

**L1：manifest 接线，零代码——解决①**

- `game_start` 加 `on_event: {"robot.grasp_cup.completed": {"to": "shake_countdown"}}`，`duration` 3.5 → 8~10s 改为**上限语义**（on_expire 建议改指 `arm_failed`：L1 后正常路径必走事件，到上限即异常）。
- 机制已齐：grasp 完成事件现在落 `robot_unrouted`（`state_machine.py:688`），`_route_robot_event` 按当前状态查表，generation 保证事件先到则 on_expire 失效。纯 manifest 改动。
- 收益：物理快了倒计时立即开始（消空窗），物理慢了倒计时自动等臂（节拍正确、整体后移）。
- **注意点（必须同步做）**：状态机层提前判死（on_expire→arm_failed）时，provider 层旧 grasp 命令仍占臂锁——manifest 的 grasp `timeout_seconds`（现 30s）要收紧到与 duration 上限一致，否则出现"状态机已判死、reset_home 在锁上排队 30s"的僵尸窗口。
- 倒计时本身 2.4s 固定不变，观众节奏不受影响。

**L2：命令粒度重切，隔离波动源——解决③④（中等改动）**

核心思想：**拆段不是为了精确对齐，而是把方差隔离**——稳定段提前跑，待对齐段缩到最小、其标定常数不再吸收前段的波动。

- **③ until=OPEN**：`shake_dice` 的 `until` 从 `RETURN_HOME` 改 `OPEN`（provider.py:475，一行），喊停锚点=手指松开（提前 ~1s）；RETURN_HOME 在 demo 后台收尾，analysis 的 8s 预算足以盖住，归位由不变量兜底。需确认 demo advance 语法支持 OPEN 作终点（见 D-3）。
- **④ 出拳两段拆**：拆成两个 manifest 动作——`throw_prep`（rps-ready 手前伸，无信息量，进 play 即发）+ `throw_gesture`（亮拳，带 delay_seconds 标定到"布"）。机制刚好拼得出：**delay 睡眠在臂锁外**（`server.py` `_round_robot_fn` 的 delay 分支在调 provider 之前），prep 执行期间 gesture 在睡，睡完抢锁准点执行——demo 零改动、引擎零改动。main 侧改动 = 契约加 `throw_prep` 命令（`core/robot.py` + `state_schema.py` ROBOT_COMMANDS + `server.py` 分发 + provider 实现，各几行）+ manifest。delay 标定对象从"整条链"缩到"单个 gesture 动作"，方差大幅缩小。
- **④ 的标定流程**：delay ≈ 布时刻(相对 wav 起点) + 浏览器起播开销(60-200ms，09-15 SSE 打戳法现成) − gesture 动作耗时 − 锁开销。不可消除项=浏览器音频 jitter，见"错位预算"。
- **抓取链预热提前量（实验性，依赖 M-1 先落地）**：rules 宣读 ~30s 足够跑完 HOME→CAPTURE→PLAN（进游戏/规则态派发 advance until PLAN），game_start 只剩 ~3s 后半链，窗口压力消失。风险与前置：预派发期间臂不在 home → 巡检会拉它回家（M-1 统一仲裁是前置）；demo 侧 flow_in_progress 会拒 reset_home → 需要"advance 中止回 home"命令（见 D-2）；玩家宣读期间动杯子 → PLAN 失效（靠 GRIP 失败重试兜底，需实验评估）。
- ②（开始↔SHAKE 同刻）：L1 落地后错位只剩状态切换+派发开销 ~200ms，**评估后大概率不做**（不值得加机制）。

**L3：时间轴编排层（真架构修改，暂不推荐）**

把"节拍剧本"从状态机挪进显式 timeline 编排器（`on LIFT → 播三二一；on OPEN → 喊停`），状态机退化为视图投影，"倒计时 N 秒要完成什么动作"成为一等公民建模。**但 L1+L2 落地后，现有 duration/on_expire/on_event 三件套已能表达同样的编排**，L3 的真实增量只剩"音画臂三流同刻并发对齐"，demo 场景用不上。建议做完 L2 再重新评估。

### 横切原则（防止过度工程化）

1. **先测量再优化**：M-3 的 per-phase 计时是本专题的前提基建。每局输出节拍表——绿键→LIFT 完成、LIFT→三二一起点、"开始"→SHAKE 起转、OPEN→"停"、（rps）"布"→亮拳——把"拿捏不准"变成均值/方差数字。桩 provider 断言编排逻辑（测试基建现成），真机跑 N 局看分布。
2. **错位预算**：观众可感知阈值 ≈200-300ms，目标是压进阈值且**方差小**，不是追求零错位——浏览器音频 jitter（起播水位 60ms + decode + 回执往返 ~90ms）决定了零错位物理上不可达。

## M-1 场外归位多触发源无统一仲裁（含巡检竞态）——`待讨论`

**问题**：发 `reset_home` 的路径四条，只有终态 watcher 有代数守卫（`_arm_reset_generation`，`server.py:883`）：

1. 终态 watcher（server.py:887）——有代数守卫 ✅
2. 失败页 / rehome 状态动作——场内，游戏自管 ✅
3. 开机归位 `_home_arm_on_boot`（server.py:943）——**不看 rounds**，靠"规则宣读比归位长"的巧合兜着
4. 30s 巡检 `_run_home_patrol`（server.py:990）——**check-then-act 竞态**

**竞态链（4 号）**：`game_live` 检查（:1045）→ `query_pose`（拿臂锁）→ 判离家 → `reset_home`（再拿臂锁，:1071）。若新回合在检查后、拿锁前创建，且游戏 `grasp_cup` 先抢到锁——臂刚 LIFT 举杯，巡检的 reset_home 随后执行，**把举着的杯子拉回 home**。窗口小但舞台上是灾难画面；且拖爆 rps `arm_throw` 的 8s 等待预算。

**改法方向**：reset_home 派发前在锁内重验"无 running 回合且无活跃 job"；或巡检/开机归位纳入 generation 方案。彻底版：**所有场外归位收敛到一个代数守卫入口**。**是 T-0 预热提前量（L2）的前置依赖。**

## M-3 per-phase 计时与 health 活性（T-0 的前提基建）——`待讨论`

**问题**：协议只有 `phase_started` 无耗时；provider `elapsed` 只覆盖命令全程；时序排障靠 demo runs 目录名/mtime 当"精确尺子"= 协议缺口被运维技巧代偿。且 `health()`（provider.py:393）只查文件存在，死常驻也报 ok；auto-retry 只认 `"Hand start"`（provider.py:653-671）无次数统计；demo 周期发的 `status` 事件被 `_dispatch` 当 informational 丢弃（provider.py:254），巡检每次 query_pose 都占臂锁往返。

**改法方向**：① demo phase 终态带耗时（→D-1），provider 把各阶段耗时放进 outcome；② health 增加 `resident alive / 重生次数 / auto-retry 次数 / 最近命令各阶段耗时`（纯内存零开销）；③ 巡检改**被动听** status/pose 推送（零锁开销，顺带收窄 M-1 竞态窗口）。

## M-4 生命周期产物无人认领（磁盘 21G 嫌疑头号）——`待讨论`

**问题**：每次 spawn 建 `datasets/game_<stamp>_<uuid>/`（provider.py:112），reset_home 每复活一次一个新目录，无清理；巡检 green_pose 每 30s ~1.7KB ≈ 5MB/天（清理未做）；demo runs 每次抓/摇都写；`web-8080.log` 无轮转（09-14 就 155MB）。磁盘 57G(09-21)→80G(09-25) 涨 21G。

**改法方向**：先 `du -sh` 定责（demo datasets/runs vs .runtime 日志）；保留策略（留最近 N 个）；归属明确——谁创建谁清理，或 provider shutdown 时扫。

## M-5 超时预算 conflated——`待讨论`

**问题**：`_run_command_locked`（provider.py:613）一条 deadline 同时盖"重生预热 6-10s + 动作 2-3s"（config `_note` 自述），收不动故障检测粒度。

**改法方向**：拆 ready deadline（spawn+预热）与 command deadline（ready 后起表）。低优先级：现行 45/120/30 够用；注意与 T-0 L1 的"manifest timeout 收紧"联动，两者一起做更顺。

## M-6 失败分类靠字符串匹配——`待讨论`

**问题**：auto-retry 认 `"Hand start"`；前端友好文案 `includes` 匹配（dice.js:278）。

**改法方向**：demo 终态事件带错误码（finger_check_failed / can_read / vision / timeout），provider 按码定重试策略表，前端按码出文案。与 D-1 一并做省事。

# 第二部分：机械臂上游仓（wangannyi/dice_demo hwj_dev——开发位；改动在上游提交后经 subtree 快照回流 main 运行位，需用户点头）

## D-1 phase 终态事件带耗时——`待讨论`

配合 M-3/T-0：`phase_completed`（或下一 phase_started）携带该段耗时；`status` 事件已在周期发，可与 pose 一起作为巡检的被动数据源（M-3 ③）。

## D-2 分段 advance 与"advance 中止回 home"——`待讨论`（T-0 L2 预热提前量的前置）

- 确认/支持 `advance until PLAN`（任意 phase 作终点）；
- 新增"中止当前 flow 并回 home"命令：现在 flow_in_progress 期间 action 一律 rejected（含 reset_home），预热提前量会破坏归位不变量——需要一条能打断 flow 的逃逸命令。
- 风险：打断运动中的臂要处理减速/持杯状态（打断时若持杯=接受掉杯，与失败归位语义一致，用户 09-24 已拍板接受掉杯）。

## D-3 `until` 终点粒度确认——`待讨论`（T-0 L2-③ 的前置）

确认 advance 语法是否支持 `until: OPEN`（手指松开）作为完成判据；若只认阶段机节点，OPEN 本就是节点，预计支持，需实测。

## D-4 反馈新鲜度透传收尾（稳定性）——`待讨论`

`shake_execution.py:137/361` + joint_execution 四处仍裸调 0.1s 默认反馈新鲜度限值，是已修四连（8034cc8/5d6f4c1/d01e83d/d3a1634）的同病根残余，摇骰中途 stale 失败的余下来源。判别口诀：报错毫秒数即生效限值。

## D-5 firmware 版本间歇读空——`待讨论`

"expects Nero firmware 1.20, got None"（CAN 读取类，09-24 17:44 对局中一次），发生在常驻 spawn 期。改法：spawn 序列对版本读取退避重试，把偶发从对局挪走；根因在 CAN 层。

## D-6 关键节拍段时长可配、可预期——`待讨论`

配合 T-0：参与节拍的动作段（SHAKE 摇骰时长、GRIP 手指闭合）时长应配置化且方差小——GRIP 现为 timed 盲等 `fast_finger_duration_s`（无位置反馈，`position_target_reached: null`），若要收紧节拍可评估加位置反馈判据（代价：传感器可靠性）。

# 明确不动的东西（2026-09-25 评审结论）

- 六命令契约骨架、一把臂锁单写者、reset_home/query_pose 的复活纪律、引擎按命令级事件路由——分层健康，优化只在缝上做，不重构（沿用 architecture-deferred 原则）。
- ②（"开始"口令↔SHAKE 同刻）暂不加机制（L1 后错位 ~200ms 低于感知阈值）。
- L3 编排层在 L1+L2 落地前不启动。

# 优先级（2026-09-25 更新：时序同步为当前最优先）
