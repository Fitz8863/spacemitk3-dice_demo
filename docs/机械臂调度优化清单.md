## 背景快照（讨论前提，2026-09-25）

- **分层骨架（判定为健康，不在优化范围内推翻）**：
  - 契约层 `backend/core/robot.py`：六命令（grasp_cup / shake_dice / feedback / throw_gesture / reset_home / query_pose），outcome 只有 completed/failed(+reason)，进度走 on_event。
  - 实现层 `backend/components/robot_arm_nero/provider.py`：常驻 `bash run.sh control --execute` JSONL 子进程 + reader 线程按 command_id 关联终态；一把 `_arm_lock` 单写者串行一切命令；"reset_home 唯一可复活死常驻 / query_pose 绝不复活" 纪律。
  - 引擎层 `backend/core/state_machine.py`：robot 动作守护线程派发、按 `robot.<command>.completed/failed` 路由到**当时所在**状态；未接线的结局落 `robot_unrouted` 观测（:688），不是错误。
  - 服务器层 `backend/server.py`：`_round_robot_fn` 胶水（arm_throw 共享槽 + delay_seconds）、终态归位 watcher（带 `_arm_reset_generation` 代数守卫）、开机归位、30s 巡检。
- **时序基线（2026-09-24 实测，demo runs 目录 mtime 法）**：
  - 抓取链（home→开摇）调参后 ~5s（调参前 6.3s）：HOME 1 / CAPTURE 1.6 / APPROACH 1 / GRIP 0.8（finger 0.5→0.3 后）/ LIFT 1.3；GRIP→LIFT 交接 0.22s 为结构性。
  - dice 窗口：game_start 3.5（3.0→3.5 用户板端调）+ shake_countdown 2.4 = **5.9s**，与链长靠手调对齐，无事件级同步。
  - 常驻冷启（spawn→ready）6–10s；config 超时预算**含**重生预热（grasp 45s / shake 120s / action 30s）。
- **已知背景问题**：
  - 磁盘 57G(09-21) → **80G(09-25)**，涨 21G 原因未查（第 4 项嫌疑最大）。
  - firmware 版本间歇读空（"expects Nero firmware 1.20, got None"，09-24 17:44 一次）。
  - demo 侧新鲜度透传：用户已修 8034cc8 / 5d6f4c1 / d01e83d / d3a1634；**仍裸调 0.1 默认**的位置 = `shake_execution.py:137/361` + joint_execution 四处。判别口诀：报错毫秒数即生效限值。

## 优化项

### P1-1 场外归位多触发源无统一仲裁（含巡检竞态）——`待讨论`

**问题**：发 `reset_home` 的路径有四条，只有终态 watcher 参与了代数校验（`_arm_reset_generation`，`server.py:883`）：

1. 终态 watcher `_watch_round_arm_reset`（server.py:887）——有代数守卫 ✅
2. 失败页 / rehome 状态动作（manifest on_enter）——场内，游戏自己负责 ✅
3. 开机归位 `_home_arm_on_boot`（server.py:943）——**不看 rounds**，靠"规则宣读比归位长"的巧合兜着
4. 30s 巡检 `_run_home_patrol`（server.py:990）——**check-then-act 竞态**

**竞态链（4 号）**：`game_live` 检查（:1045）→ `query_pose`（拿臂锁）→ 判离家 → `reset_home`（再拿臂锁，:1071）。若新回合在检查后、reset_home 拿锁前创建，且游戏的 `grasp_cup` 先抢到锁——臂刚 LIFT 举杯，巡检的 reset_home 随后执行，**把举着的杯子拉回 home**。窗口小（query_pose 往返 + 线程调度），但舞台上是灾难画面；且会拖爆 rps 侧 `arm_throw` 的 8s 等待预算（`games/rps/pipeline.py` `_ARM_THROW_PENDING_WAIT_SECONDS`）。

**改法方向**：reset_home 派发前在锁内重验"无 running 回合且无活跃 job"；或巡检/开机归位也纳入 generation 方案。更彻底：**所有场外归位收敛到一个代数守卫入口**，场内保持现状。

### P1-2 时序编排是"开环定时"，应改事件驱动交接——`待讨论`

**问题**：同步方式 = 并行窗口 + 手调常数。`game_start` duration 3.5 与抓取链同时起跑，倒计时一到就放行 `shake_countdown`，臂是否真就位无关紧要。09-24 那轮调参（game_start 3.0→3.5、finger 0.5→0.3）本质是用 duration 逼近物理时长；6.3s 链 vs 5.4s 窗口的问题会随换桌/温度/常驻冷热反复回来。rps 同病：口令 wav 2.64s vs 出拳耗时，靠 `delay_seconds`（现值 0.0）手调。

**关键观察**：引擎机制已齐——`game_start` 里 grasp 完成事件现在落 `robot_unrouted`（state_machine.py:688），只是 manifest 没接线。

**改法方向**：`game_start` 增加 `on_event: {"robot.grasp_cup.completed": {"to": "shake_countdown"}}`，`on_expire` 降级为超时上限；倒计时长固定 2.4s 不变（观众节奏不受影响，"三二一"永远在臂就绪后才响）。rps 可同模式评估。注意点：`duration` 语义是"on_enter 发完后起表"，事件提前到时定时器随之作废（generation 已处理），需确认无回退路径。

### P2-3 per-phase 计时与 health 活性（可观测性）——`待讨论`

**问题**：协议只有 `phase_started`，没有 per-phase 耗时；provider 的 `elapsed` 只覆盖命令全程。时序排障靠 demo runs 目录名/mtime 当"精确尺子"= 协议缺口被运维技巧代偿。且：

- `health()`（provider.py:393）只查文件存在，死常驻也报 ok；
- auto-retry 只认 `"Hand start"` 字符串（provider.py:653-671），无次数统计；
- demo 本就周期发 `status` 事件，`_dispatch` 当 informational 丢弃（provider.py:254）；巡检每次 query_pose 都要占臂锁一个往返。

**改法方向**：① demo 在 phase 终态带耗时、provider 把各阶段耗时放进 outcome；② health 增加 `resident alive / 重生次数 / auto-retry 次数 / 最近命令各阶段耗时`（纯内存读取零开销）；③ 巡检改**被动听**周期 status/pose 推送，零锁开销，顺带收窄 P1-1 竞态窗口。

### P2-4 生命周期产物无人认领（磁盘 21G 嫌疑头号）——`待讨论`

**问题**：每次 spawn 建 `datasets/game_<stamp>_<uuid>/`（provider.py:112），reset_home 每复活一次一个新目录，无清理；巡检 `green_pose` 每 30s 落 ~1.7KB ≈ 5MB/天（清理未做）；demo runs 目录每次抓/摇都写（CAPTURE 帧/快照嫌疑大）；`web-8080.log` 无轮转（09-14 就 155MB）。三天涨 21G 单靠 pose 解释不了。

**改法方向**：先 `du -sh` 定责（demo 侧 datasets/runs vs .runtime 日志）；然后保留策略（留最近 N 个 session/runs/pose），归属明确——谁创建谁清理，或 provider shutdown 时扫。

### P3-5 超时预算 conflated（重生预热与动作共用一条 deadline）——`待讨论`

**问题**：`_run_command_locked`（provider.py:613）的 deadline 同时盖"重生预热 6-10s + 动作 2-3s"（config `_note` 自己写了），想收紧故障检测粒度做不到——Detecting a hung chain in 15s 会误杀合法重生。

**改法方向**：拆两条钟——ready deadline（spawn+预热）与 command deadline（ready 之后才起表）。低优先级：现行 45/120/30 够用，只在想要更快失败检测时做。

### P3-6 失败分类靠字符串匹配——`待讨论`

**问题**：auto-retry 认 `"Hand start"`；前端友好文案 `includes` 匹配（dice.js:278 `friendlyRobotFailure`）。新增可自愈故障要改两处字符串。

**改法方向**：demo 终态事件带错误码（如 `finger_check_failed` / `can_read` / `vision` / `timeout`），provider 按码定重试策略（自动重试表），前端按码出文案。与 P2-3 一并做省事。

### P3-7 demo 侧新鲜度透传收尾（稳定性）——`待讨论`

**问题**：`shake_execution.py:137/361` + joint_execution 四处仍裸调 0.1s 默认反馈新鲜度限值，是已修四连（8034cc8/5d6f4c1/d01e83d/d3a1634）的同病根残余，摇骰中途 stale 失败的余下来源。属 demo 仓（hwj_dev），改动需用户点头。

### P3-8 firmware 版本间歇读空——`待讨论`

**问题**："expects Nero firmware 1.20, got None"（CAN 读取类，09-24 17:44 对局中一次）。发生在常驻 spawn 期，偶发落进对局。

**改法方向**：boot homing 时探测 + 退避重读，把偶发从对局挪走；或 demo 侧 spawn 序列里对版本读取重试。根因在 demo/CAN 层。

## 明确不动的东西（2026-09-25 评审结论）

- 六命令契约、一把臂锁单写者、reset_home/query_pose 的复活纪律、引擎按命令级事件路由——分层健康，优化只在缝上做，不重构（沿用 architecture-deferred 原则）。

## 优先级（首轮建议）

① P1-1 竞态（正确性，改动薄） → ② P1-2 事件驱动（消灭调参） → ③ P2-3 观测性 → ④ P2-4 清理 → ⑤ P3 按需。
